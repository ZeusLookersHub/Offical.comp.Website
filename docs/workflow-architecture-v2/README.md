# Lookers AI — Workflow Architecture v2

**حزمة تصميم قابلة للفحص، مش إعلان إن النظام الجديد اتوصل بالشات.**

الأساس اللي راجعناه: `feature/lookers-ai-expanded-orbits` عند commit `32194938197f501843ef0b62b65cf28d00bff5e1`.

الموجود حاليًا 138 موضوعًا مسجلًا و14 عائلة أسئلة؛ 40 اختيارًا ظاهرًا في الكواكب بيمثلوا 38 موضوعًا مختلفًا. التجربة الحالية بتجهز برومبتات من مقابلة محددة بالكود، وبعد فحص Agent.run() بتستدعي مسار التوليد الحالي. توسعة أسماء الاختيارات وحدها لا تثبت جودة التخصص أو جودة الصورة النهائية.

## الهيكل الجديد

- **13 كاتيجيري وظيفية** تحت أربع مجموعات للمراجعة، من غير فرض تغيير للكواكب الخمسة أو الهيدر.
- **45 فرعًا**، و138 مهمة بمعرف ثابت ومكان أساسي واحد. عرض نفس المهمة من مدخل تاني يتم كرابط، مش نسخة من التعريف.
- **8 أنماط مشتركة** تجمع شكل العملية: إنشاء، تعديل، تواصل، تخطيط، بحث، تحليل، مستند منظم، ومواصفات تقنية.
- **16 blueprint مفصلًا** كبداية للتخصص، لكل واحد أسئلة مدخلات، خطوات خاصة، بوابة جودة، ناتج محدد ودورة مراجعة. دي أمثلة تصميم عميقة؛ الأمثلة دي تغطي 49 موضوعًا، والـ89 موضوعًا الباقيين لسه محتاجين تفصيل متخصص قبل ادعاء اكتمال التغطية.
- **47 وحدة سؤال مشتركة**، لكل وحدة سؤال وشرح ومثال بالعربي والإنجليزي، وسياسة سؤال الناقص المناسب فقط. تعريفات تصميم لم تُوصل بالـruntime بعد.
- **11 علاقة بين المسارات** بقائمة حقول وأنواع ومصدر واضح. الربط مصمم لاختيار السياق ومراجعته يدويًا؛ لا يشغّل مسارًا آخر تلقائيًا.

التصنيف يجاوب «أدور فين؟»، والـpattern يجاوب «نوع العملية إيه؟»، والـblueprint يحدد «إيه الخطوات والأسئلة؟»، وعقد المخرج يحدد «هستلم إيه؟». ريبو الرسم مش مسؤول عن اتخاذ القرار أو تنفيذ أدوات.

## مثال اختبار العطر

المهمة → صورة منتج → تثبيت المنتج والبراند → مرجع الهوية → تكوين وإضاءة → سياسة الكتابة → إعدادات الأداة → فحص البرومبت → مراجعة النتيجة.

المقاس واسم الأداة ومصدر التوليد بيانات تنفيذ/عرض؛ مش عناوين في المشهد. النص داخل الصورة اختياري افتراضيًا، وما يظهرش إلا بنص مؤكد بالحرف. لو المقصود DAVIDOFF، ما يتحولش إلى DAVIE DOVE أو اسم عربي متخيل. لو دقة الكتابة غير مضمونة في أداة الصور، نحتفظ بالمرجع المعتمد أو نجهز مساحة لإضافة اللوجو في خطوة تحرير. فحص مواصفة البرومبت مختلف عن فحص بكسلات الصورة؛ الدقة النهائية محتاجة اختبار توليد وقراءة النص الناتج ومراجعة بشرية.

## مثال ربط مفيد

بريف هوية → بريف صورة منتج → بريف فيديو → بريف حملة → نصوص القنوات. اللي بيتنقل هو حقول مختارة بمصادرها، مش كل المحادثة، ومش حقائق مخترعة من مخرج AI غير مراجع. مخرج بريف الصورة مش صورة مولّدة ولا أصلًا بصريًا معتمدًا.

## ترتيب التنفيذ

1. إصلاح فصل النص الظاهر عن بيانات التنفيذ والاسم الحرفي، وبناء regression set من اختبار العطر.
2. تحويل التصنيف إلى registry واحد، وربط كل موضوع بـpattern وmodules ونسخة blueprint.
3. بناء عقود المراحل والمخرجات والشروط والتحقق من الجراف قبل توصيله.
4. وصل تعريفات الأسئلة والهنتات بالمقابلة الحالية، مع سؤال واحد وتخطي الإجابات الموجودة.
5. فصل copyablePrompt عن displayMetadata وعن executionConfiguration، مع adapters للأدوات.
6. مقارنة baseline قديم/جديد على حالات عربية وإنجليزية، ثم تقييم حي محدود واضح التكلفة.
7. محرر داخلي بـReact Flow وتخطيط ELK إذا اجتاز PoC؛ واجهة المستخدم تفضل بسيطة.
8. إعادة استخدام السياق بين المسارات بعد اختيار ومراجعة المستخدم. تشغيل أدوات أو إيجنتات متعددة يفضل في Phase 2.

## معيار القوة

لا ندّعي «أقوى من كل الموجود» من غير benchmark. شرط الإصدار المقترح: صفر أخطاء حرجة في أسماء البراند والنصوص المؤكدة وتسريب بيانات التنفيذ؛ جميع الحالات المطلوبة تصل للمخرج الصحيح؛ لا تكرار أسئلة لإجابات مؤكدة؛ وكل مسار له أمثلة نجاح وفشل وحدود واضحة. التقييم الحتمي يقيس العقد، ومراجعة الموديل تقيس المعنى، وتجربة الأداة الفعلية تقيس النتيجة النهائية. أي درجات جودة رقمية تحتاج نتائج فعلية محفوظة.

## الملفات والتحقق

- `architecture.json`: التصنيف والأنماط والمسارات والعلاقات وعقود النصوص.
- `REPOSITORIES.md`: قرار استخدام 25 ريبو مع الروابط والرخص وحدود الملاءمة.
- `repository-evidence.json`: لقطة metadata بتاريخ البحث + التقييم الهندسي.
- `validate.py`: تحقق الترابط والتغطية وحدود المرحلة و31 اختبارًا حتميًا، منهم حالات اختبار العطر.
- `review.zip`: الرسومات وصفحة المراجعة والمواصفات وتقاريرها، بعد التوليد.

تشغيل الفحص: `python docs/workflow-architecture-v2/validate.py`. نجاح الاختبارات لا يثبت توليدًا حيًا أو تطابق كتابة الاسم في الصورة. لم نثبت أطر تشغيل جديدة داخل التطبيق، ولم نعدل الهيدر أو الصفحة الرئيسية أو إعدادات الإنتاج.

التوليد: `python scripts/build-workflow-architecture.py --out .archify/workflow-review`، ثم Archify finalize لكل job. مصدر Archify المستخدم: `tt-a1i/archify@f325d86230553e1dd15d3464324f1fcd01f02352`. فحص صفحة المراجعة: `node scripts/qa-workflow-architecture.mjs <absolute-output-directory>` مع Playwright متاح. تقارير المصدر تحتفظ بمسارات الإنشاء الأصلية؛ النسخة المصدرة منقولة كما هي للمراجعة.
